# PR stacks

A large diff is hard to review. Ship work as a **stack**: an ordered chain of small PRs that all serve **one objective** (for example, one feature). Each PR builds on the one before it and can be reviewed on its own.

## 1. Plan before you build

Do not write code until the stack plan is posted and the reviewer has had a chance to weigh in.

1. **State the objective** in one sentence. If the work has two objectives, it is two stacks. An unrelated fix noticed along the way gets its own standalone PR, never a slot in the stack.
2. **List what needs to be implemented**: the modules, data, tests and docs the objective needs.
3. **Divide that list into PRs.** Each PR:
   - does one thing that can be explained in a sentence ("add the reward formula", not "core pieces");
   - touches **at most about 6 hand-written files** (source, tests, docs). If it needs more, split it again;
   - puts generated or data files (fixtures, manifests, recorded results, lockfiles) in a PR of their own, or lists them clearly as generated so the reviewer can skim them;
   - ships with its own tests and leaves the main branch working if merged alone;
   - depends only on PRs earlier in the stack.
4. **Order the stack** from the foundations up: data and types, core logic, integration, interfaces (CLI and API), then docs and results.
5. **Post the plan** as a short numbered list. Give each PR a title, its files, what it adds, and its tests. Wait for the reviewer's input on the split before opening PRs.

Plan template:

```
Objective: <one sentence>

1. <PR title>: <what it adds>
   Files: a.py, test_a.py
   Tests: <what they check>
2. <PR title>: ...

Standalone (not in the stack): <unrelated fixes, if any>
```

## 2. Build the stack

- Make one branch per PR. Each branch starts from the previous PR's branch, and the first one starts from the default branch. Name them `<stack-name>/<n>-<slug>`, for example `futurebench/1-task-manifests`.
- Set each PR's base to the previous PR's branch, so its diff shows only its own changes. The first PR's base is the default branch.
- Run the repo's tests on every branch before you push it.
- When an earlier PR changes during review, merge it into each later branch in order (no force-push on shared branches) and push.
- After a PR merges, retarget the next PR's base to the default branch.

## 3. Write each PR description in this format

Use these five sections, in this order, with these exact headings:

```
## What's in this PR
<Summary of the changes, and how they contribute to the stack's objective.>

## Files to Review
`path/to/file.ext`
- <change 1>
- <change 2>

`path/to/other.ext`
- <change 1>

(Generated or data files, if any: list them under one line saying how they were produced, e.g. "tasks/*.json: generated by `python -m pkg.build_tasks`".)

## How to test
<A copy-pastable command, or a few steps to set up an environment and run a test.>

```
pip install -e '.[test]'
pytest tests/test_reward.py -q
```

## Test Cases
`tests/test_file_1.ext`
- added test `test_name_1` to check <behavior>
- added test `test_name_2` to check <behavior>

## Milestone
PR <n> of <N> in the <stack name> stack: <objective>.
- Before this: #<pr> <title>
- After this: <next PR title> (planned or #<pr>)
```

Rules for the description:
- "Files to Review" names every hand-written file in the diff, each with what changed in it.
- "How to test" must actually work when pasted. Run it yourself first.
- "Test Cases" names each new or changed test. If the PR adds no tests, say why (for example, docs only).
- Keep any attribution lines the repository or session requires above these sections.

## 4. Splitting a PR that is already too big

1. Group its files by purpose, then write the stack plan as in step 1 and post it.
2. After the plan is agreed, build the branches by checking out files from the big branch in plan order (`git checkout <big-branch> -- <files>`), committing each group on its own branch.
3. Open the stacked PRs, then close the big PR with a link to the first PR of the stack. Ask before closing it if someone else opened it.
